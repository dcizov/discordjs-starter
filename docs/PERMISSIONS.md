# Discord permissions and practical setup

This matrix is derived from the installed Discord.js code and Orbit's actual handlers, not the Developer Portal's permission calculator. See `packages/core/src/permissions.ts`, `apps/bot/src/{index,sync,roles,shop,moderation,automod,music,interactions}.ts`, `apps/worker/src/index.ts`, and `apps/web/lib/auth.ts`.

## Six different layers — do not conflate them

| Layer                              | What this implementation uses                                                                                                                                                                                                         | What it does NOT prove                                                                                                                                                                                          |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Application installation           | OAuth scopes **bot** + **applications.commands**. The dashboard invite now requests basic channel posting bits **19456**: View Channel + Send Messages + Embed Links.                                                                 | A requested invite mask is not the bot's effective current guild/channel permissions. Existing installations are not changed automatically. Pure interaction replies do not require this entire posting preset. |
| Bot permissions                    | The installed bot's guild roles, plus category/channel/member overwrites for the destination.                                                                                                                                         | Channel allows do not confer guild-wide Kick/Ban/Moderate/Manage Roles authority. Administrator is never the recommended setup.                                                                                 |
| Gateway intents in code            | **Guilds, GuildMembers, GuildMessages, MessageContent, GuildMessageReactions, GuildVoiceStates**, from the shared `gatewayIntentNames` list.                                                                                          | Permissions in an invite do not enable intents. Presence is not requested.                                                                                                                                      |
| Portal privileged intents          | Enable **Server Members Intent** and **Message Content Intent** for the current runtime, which requests both even when individual modules are paused. Large verified applications may require Discord approval.                       | **GuildVoiceStates is not privileged and has no Portal toggle.** There is no voice intent switch to enable here.                                                                                                |
| Command and internal authorization | Command default-member permissions, current actor permissions, module state, target hierarchy, self-role policy, music same-channel and DJ checks.                                                                                    | A visible command, a successful `/ping`, or dashboard access does not grant permission to execute another action. Discord integration command overrides can affect visibility, not bypass runtime checks.       |
| Dashboard login                    | OAuth **identify + guilds**; the selected server's owner, Manage Server, or Administrator can configure it. Reads have a short permission cache; mutations bypass a positive cache and fail closed if re-verification is unavailable. | These are the human user's OAuth permissions, not bot permissions. The bot rechecks actor/target/channel restrictions when executing queued actions.                                                            |

**The Portal screenshot's Bot Permissions integer `0` is an invite-URL calculator, not a live audit.** Changing its checkboxes does not retroactively modify an installed bot's role. Check the real server's role and destination overwrites instead. An application ID is not a token; never paste tokens, secrets, voice session IDs or raw voice payloads into a report.

No feature needs Administrator; the bot does not need Manage Server, Manage Channels, or Discord Manage Webhooks for the implemented workflows.

GuildMembers is requested by the current combined bot runtime for member/role behavior. Fetching one member by REST, a Portal privileged-intent setting, and a channel permission are not the same thing; do not infer one from another.

The new community modules are **disabled until explicitly enabled**, including configurations written before their keys existed. Grant Send Polls only to chosen poll destinations, not Administrator or a larger invite mask. No new privileged intent is needed. Poll votes remain native Discord data; Orbit stores aggregates only. Community setup, schedule cancellation/expiry, actor revalidation and data retention are detailed in [COMMUNITY.md](COMMUNITY.md).

## Practical setup in Discord

1. **Keep credentials server-side.** Select the application matching `DISCORD_CLIENT_ID` / the bot token in your protected environment. Set the exact OAuth callback (for local development, `http://localhost:3000/api/auth/callback`). Dashboard login uses identify + guilds; installation uses bot + applications.commands.
2. **Enable the two actual privileged intents** under the application's Bot page: Server Members and Message Content. Do not search for a privileged voice toggle. Restart the intended bot if changing intents/configuration.
3. **Install with the minimal posting invite.** The generated mask is `19456`. Review the real installed role afterward: old invitations may have requested the previous all-feature mask `1099783302214`, which also included role/moderation/voice permissions. Changing the new invite does not silently remove or grant any existing permission.
4. **Set the Orbit role's hierarchy deliberately.** Put it above only the safe community/shop roles and ordinary members it is meant to manage, below trusted staff as appropriate. Grant Manage Roles only for role features; Moderate Members for warnings/timeouts; Kick/Ban only when used. Never make a staff/integration role self-assignable.
5. **Check each destination in Edit Channel → Permissions**, including its parent category's synchronization and explicit member/role overwrites. Give text destinations View Channel, Send Messages, Embed Links. Add Read Message History only where panel refresh/reaction/purge needs it; Manage Messages only in moderated/purge channels. Test a dedicated normal non-full voice channel with View Channel, Connect and Speak.
6. **Register commands once in the intended scope.** The read-only Commands dashboard shows definitions, not live registration. Guild-scoped development commands update quickly. Check Server Settings → Integrations / command availability and the human member's application-command permissions if commands are hidden.
7. **Inspect Channels & roles → Permissions** after the bot syncs. The view is read-only and reports the selected channel's effective Discord.js permission bitfield, bot-role baseline, hierarchy protections and code-derived intent/actor notes. New metadata uses the existing JSON columns; no schema migration/reset is needed. Legacy snapshots are **Not verified** until refreshed. Demo is explicitly **Sample data**. Role/channel events and bot role-membership changes trigger sync, with a five-minute scheduled fallback; this is not a live audit or a Portal-intent verifier.
8. **Test only with authorized disposable targets.** A low community role, a non-staff test member, an item-only purchase, one explicit source test message and one permitted clean recording in the test voice channel are appropriate. Do not test destructive moderation on production members. Inspect Audit/delivery diagnostics for the actual failed stage.

The read-only channel/role export utility is documented in [CHANNEL_EXPORT.md](CHANNEL_EXPORT.md). It exports configured roles/overwrites, **not** calculated effective permissions for every member. Keep its output private.

## Docker-only update and registration

Use one gateway process, not both a host/editor bot and a Compose bot with the same token. The Dev Container editor service is idle by default; it does not automatically log in. The following is the **development Compose override** (its image contains the TypeScript CLI); npm runs **inside containers**, not on your host:

```sh
# First update this checkout to the intended branch/head without discarding local edits.
git fetch origin
git pull --ff-only origin arena/e2b42b08-discordjs-starter

docker compose -f docker-compose.yml -f docker-compose.dev.yml --profile live --profile music up -d --build
# REST-only registration; this does not create a second gateway session.
docker compose -f docker-compose.yml -f docker-compose.dev.yml --profile live --profile music run --rm --no-deps bot npm run commands:register
# Read-only backend/source diagnostics; does not join Discord or play audio.
docker compose -f docker-compose.yml -f docker-compose.dev.yml --profile live --profile music run --rm --no-deps bot npm run music:doctor

docker compose -f docker-compose.yml -f docker-compose.dev.yml --profile live --profile music ps
docker compose -f docker-compose.yml -f docker-compose.dev.yml --profile live --profile music logs --tail=150 bot worker
```

For the **production runtime image** without the development override, use `node dist/register.js` and `node dist/music-doctor.js` inside the equivalent one-off bot container instead of the TypeScript npm scripts. Omit the music profile only if music is intentionally unused. Set `DEMO_MODE=false` only in your protected live environment; demo never logs in or sends audio/messages.

Rebuilding does **not** fetch Git. Development bind mounts can override the image with an older checkout. Existing Discord messages keep their old embeds. Current presentation/permission changes do not change slash definitions; registration is needed if your deployment predates the title-autocomplete definitions. Do not rotate credentials, reset the database, delete volumes, or run `down -v` as a troubleshooting step.

## Remaining live checks

No bot credentials or authorized guild were available during this implementation. Synced metadata and offline fixtures cannot certify Portal settings, another machine's gateway processes, live channel hierarchy, actual Discord handshake, provider access or audible playback. The repository's Compose/editor contract was inspected and tested: only the bot service starts the intended gateway; registering commands and running the doctor do not. Separately started host/editor processes or stacks using another Redis/environment cannot be discovered from this sandbox. Verify them explicitly without dumping tokens, environment secrets or raw voice packets.
