## Implemented image and identity path

1. **Server-only URL boundary:** `lib/discord-images.ts` validates snowflakes/hashes and uses the installed public `discord.js.CDN` API. Icons and **global** avatars use static WebP, size 128, including animated hashes (`forceStatic: true`). No guild-member avatar lookup, new OAuth scope, discriminator guessing or new image service. No new dependency.
2. **Public DTO:** `publicUser` explicitly projects only id/name/avatar/avatarUrl. Raw icon/avatar hashes remain compatible; optional `iconUrl`/`avatarUrl` are additive. No session ID, OAuth grant, token, cookie or secret is serialized to the dashboard. Exact local demo paths work only in demo mode.
3. **Current guild display:** the authorized OAuth guild name/icon override an older bot snapshot for the selected guild and switcher. Existing guild authorization/cache TTL is retained. `GuildUpdate` invokes the existing persistence sync; periodic sync remains. Icon removal overwrites the previous hash with null.
4. **Renderer:** a small shared `IdentityImage` uses Next Image, 28/30/33px fixed frames, empty decorative alt and meaningful parent control names. The frame includes its border (a 33px frame has a 31px inner image). Initials stay underneath until load; error removes the broken image. Identity/source keys reset failure when metadata changes. The dashboard workspace is keyed by guild **and** account so drafts/local state do not leak across those boundaries. Same-workspace optimistic/poll reconciliation remains.
5. **Explicit profile metadata refresh:** the account menu calls `POST /api/auth/profile`; it is not part of passive dashboard polling. Origin → signed-in identity → 5/minute user limiter → existing bounded body parser + strict empty schema → Discord own profile → account-ID check → SQL update matching session ID, user ID and unexpired session → public DTO. It never updates another account or recreates a revoked session. Tokens/expiry are not changed by this metadata action. Errors log status only; generic upstream failures are recoverable 503, revoked sign-in is 401. No browser-supplied user/guild/session/profile selector is accepted.
6. **Account mismatch:** a different-account profile/dashboard response triggers server router reauthorization rather than merging the foreign snapshot into an existing workspace. This is not a claim of instant cross-tab cookie-change detection or a real second-account login test.
7. **Next protections:** allow only HTTPS `cdn.discordapp.com`, empty port, `/icons/*/*.webp` or `/avatars/*/*.webp`, exactly `?size=128`. SVG remote images, arbitrary hosts, attachments and other queries remain rejected. Global API responses explicitly use `private, no-store`; meaningful SSR/no-JS navigation remains available (removed the dashboard-wide pre-hydration `inert`, not server rendering).

**Demo is separate:** original fictional local SVG art demonstrates the Cozy Corner icon and Jamie avatar, with “sample image” in the demo account menu. Other guilds still demonstrate the no-icon fallback. Existing demo files are not reset/migrated or overwritten; the sample guild icon applies to a fresh seed. No live Discord call/message/audio occurs in demo. An unchanged previously failed URL is retried on remount/reload, **not** by merely refreshing identical metadata; changed URLs reset automatically. No polling/retry loop is added.

## CI-discovered contrast correction

The first new implementation commit, `36f577fa78ff160f99fe557aa0c1687313c6282a`, ran [CI 40200928215](https://github.com/dcizov/discordjs-starter/actions/runs/40200928215). **Containers passed**: runtime/dev images, Compose profiles, unprivileged offline CLI, all nine pinned plugins + Soundy, supervised backend WebSocket/readiness and the real Dev Container without a second bot. Verification passed real PostgreSQL units/type/lint/audit/build but the standard-browser suite was **44 pass / 1 fail**: Community scoped text contrast. The earlier local Chromium 153 green was not treated as proof that this was harmless.

Reproduction before changing CSS: six small palette tests calculated WCAG sRGB contrast from the existing HSL tokens **without rounding channels**. Two failed: light muted text was **4.4934:1 on body** and **4.2798:1 on the muted surface** (minimum 4.5). Local Chromium's displayed integer channels gave a misleading 4.5168 body ratio. This is a real margin defect, not grounds to weaken axe.

**Correction:** light `--muted-foreground` lightness 48% → 45%; dark colors unchanged. Exact ratios are now about **4.99:1 body / 4.75:1 muted**, with six palette tests passing. Community axe now waits for actual font readiness and currently running finite animations to finish, avoiding intermediate page/dialog fade colors; it does not sleep, disable motion, alter timeouts, exclude nodes or relax rules. Dark/light checks assert the actual theme, and failures include contrast diagnostics. No application SSR/content-hiding change. Full units, both production modes and all browsers are rerun on the corrected source; final immutable CI run is supplied with the delivery.

## Guarantees deliberately retained

No changes to the publication core, atomic SQL claim/settlement, versioned intent keys, stale/concurrent job rejection, bounded schedule/expiry windows, ambiguous-send/no-blind-replay handling, mention suppression, actor/channel revalidation, paused cleanup, short transactions, voice attempt ownership/cleanup or retry boundaries. No schema, persistent config, public command, grant mask, plugin/source ownership or queue protocol changes. No resets, destructive migrations, live demo side effects or extra gateway client.

Large resource/dashboard files, genuine optimistic reconciliation effects and separately authorized handler/executor/database checks are **not** mechanically merged. Background dashboard refresh error presentation and token-refresh concurrency remain separate existing design topics, not a claim that every catch/error/lifecycle concern was fixed. Existing tests were extended, not deleted or replaced with snapshots of implementation structure.

### Security audit caveat

A fresh full `npm audit` still reports **10 affected development packages: 8 moderate, 2 critical**, including transitive Tinypool and Vitest. Production-only audit reports zero; that is **not** “the whole dependency tree is clean.” Tinypool advisories [GHSA-5gmw-xhrv-c9v3](https://github.com/advisories/GHSA-5gmw-xhrv-c9v3) and [GHSA-85c8-ppgw-ccpr](https://github.com/advisories/GHSA-85c8-ppgw-ccpr) require 2.1.1/2.1.2 respectively; npm's recommended Vitest remediation is a major v5 upgrade. Other suggestions include major/downgrade toolchain changes. Do **not** run `audit fix --force` or silently pin an incompatible worker pool as part of an image refactor. These pre-existing development-tool findings need a separately verified toolchain upgrade; they are not waived as harmless. This task ran trusted-repository one-shot CLI tests, not a publicly exposed Vitest API/UI, Drizzle Studio or esbuild development server. Do not expose those tools to untrusted networks/data.
